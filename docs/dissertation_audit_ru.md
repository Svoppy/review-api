# Аудит проекта для доведения до уровня диссертации

Дата аудита: `2026-05-28`

## 1. Текущий статус

Проект `ReviewGuard` уже представляет собой хороший исследовательский MVP:

- есть единая структура репозитория;
- реализован конвейер `data -> training -> export -> API -> web UI`;
- есть baseline, single-task и multitask training scaffolds;
- есть тесты для нормализации данных, метрик и inference-артефактов;
- есть черновики статьи, архитектурные заметки и roadmap.

Для диссертации этого достаточно как основы, но недостаточно как финального исследовательского результата. Основной дефицит сейчас не в архитектуре проекта, а в полноте доказательной базы.

## 2. Сильные стороны

### 2.1. Инженерная часть

- Репозиторий структурирован логично и читаемо.
- Код разделен на понятные модули: `data`, `ml`, `training`, `api`.
- Поддерживается частичная разметка, что хорошо соответствует постановке multitask-задачи.
- Есть экспорт модели и отдельный inference-слой для API.
- Есть прозрачный explainability-блок с вероятностями и признаком усечения текста.

### 2.2. Научная постановка

- Тема актуальна для e-commerce и 2026 года.
- Связка `sentiment + authenticity` выглядит осмысленной и защищаемой.
- Выбран practical multitask setup: общий encoder и две task-specific головы.
- Правильно зафиксирована неоднородность authenticity datasets и ограничения их интерпретации.

## 3. Критические пробелы перед сдачей

### 3.1. Нет финальных экспериментальных результатов

Сейчас в репозитории есть только pilot baseline и заготовки под обучение. Для защиты этого недостаточно. Нужны:

- полноценные прогоны на финальных данных;
- итоговые таблицы метрик;
- сравнение `baseline vs single-task vs multitask`;
- как минимум одна ablation-study;
- error analysis по типовым ошибкам.

Без этого работа выглядит как качественно реализованный прототип, а не как завершенное исследование.

### 3.2. Недостаточная воспроизводимость в дефолтном запуске

До правок тесты не запускались "из коробки":

- `pytest` не видел пакет `reviewguard`;
- временные директории pytest падали из-за недоступного системного temp-path.

Для диссертации это особенно чувствительно, потому что воспроизводимость должна быть подтверждаема не на словах, а на практике.

### 3.3. Статья пока сильнее как черновик, чем как публикационный текст

По содержанию черновик уже добротный, но перед подачей обязательно нужно усилить:

- формализацию научной новизны;
- четкое описание вклада автора;
- явное описание экспериментальных гипотез;
- таблицы результатов;
- обсуждение статистической устойчивости результатов;
- ограничения исследования и угрозы валидности;
- связь между исследовательской частью и веб-системой как прикладным результатом.

## 4. Что нужно сделать в первую очередь

### Приоритет A: обязательно

1. Провести финальные эксперименты на полном наборе корпусов.
2. Сформировать итоговые таблицы по всем моделям и датасетам.
3. Добавить confusion matrices и краткий error analysis.
4. Зафиксировать точный experimental protocol:
   - split policy;
   - random seed;
   - model backbone;
   - learning rate;
   - batch size;
   - epochs;
   - hardware/software environment.
5. Переписать раздел результатов статьи так, чтобы каждый тезис опирался на таблицу или рисунок.

### Приоритет B: очень желательно

1. Сделать ablation по `loss_weights`.
2. Проверить влияние multitask-learning на sentiment и authenticity по отдельности.
3. Добавить diagram архитектуры системы.
4. Привести библиографию к единому стандарту вуза или журнала.
5. Подготовить отдельный раздел "Практическая значимость".

### Приоритет C: если останется время

1. Добавить calibration/error bars или хотя бы повторные прогоны на нескольких seeds.
2. Включить небольшой ручной qualitative analysis сложных отзывов.
3. Расширить discussion по AI-generated reviews как современной угрозе.

## 5. Рекомендованная структура финальной статьи

Оптимальная структура для сильной диссертационной статьи:

1. Введение и постановка проблемы.
2. Анализ литературы и существующих подходов.
3. Формальная постановка multitask-задачи.
4. Описание данных и unified schema.
5. Архитектура модели и веб-системы.
6. Дизайн экспериментов.
7. Результаты и сравнение моделей.
8. Error analysis и обсуждение.
9. Ограничения и угрозы валидности.
10. Заключение с научной и практической ценностью.

## 6. Что уже можно уверенно защищать

Уже сейчас можно уверенно защищать следующие тезисы:

- постановка задачи корректна и актуальна;
- архитектурное решение выбрано рационально;
- репозиторий отражает воспроизводимый pipeline;
- единая схема данных является полезным исследовательским артефактом;
- мультитаск-подход инженерно оправдан с точки зрения стоимости inference и сопровождения.

## 7. Что пока защищать рано

Пока рано делать сильные итоговые заявления о превосходстве multitask-модели, потому что в репозитории еще нет достаточного количества финальных результатов для доказательства:

- прироста качества;
- устойчивости к разным типам fraud;
- переносимости между доменами;
- статистической надежности вывода.

Оценка текущего состояния:
